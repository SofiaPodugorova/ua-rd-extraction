# AGENTS.md

## Общие правила

- Общаться с владельцем репозитория только по-русски.
- В проекте два независимых процесса: сбор исходных PDF и построение табличных
  данных. Для обоих полный целевой диапазон — 1991–2025 годы включительно.
- Не смешивать исправления загрузчика PDF с изменениями схемы таблиц без прямой
  просьбы пользователя.
- Не добавлять PDF и ZIP в Git: это многогигабайтные рабочие данные.

## Сбор PDF

- Рабочие файлы: `download_nrat_pdfs.py` и
  `NRAT-Scraping&log-FULL-YEAR-clean.ipynb`.
- Годовые ZIP хранятся вне репозитория, в соседней папке `../nrat pdfs`.
- Активная коллекция после консолидации должна содержать ровно один канонический
  архив `<год>.zip` на каждый год 1991–2025. Исходные части из резервной папки
  `_pre_consolidation_<UTC>` не считать активными архивами.
- Корректные существующие архивы года нужно пропускать. Имя может быть как
  `<год>.zip`, так и `<год>-<служебный суффикс>.zip`.
- Исключение — явный режим `--repair`: он обязан индексировать все архивы года
  по `doc_id`, игнорировать старые `_progress_check_*.json` и создавать новый
  patch-ZIP только с отсутствующими PDF. Исходные ZIP не перезаписывать.
- Обход выдачи выполняется по одному дню. Параметр пагинации сайта — `pa`, не
  `page`.
- Не уменьшать паузы 3 секунды между страницами, 1 секунду между файлами и
  5 секунд между днями. Не распараллеливать запросы к НРАТ.
- Не отмечать день завершённым, если страница выдачи не загрузилась, не прошла
  проверку, повторила предыдущую страницу либо какой-либо PDF завершился со
  статусом `fail`/`empty`.
- Исключение по прямому решению пользователя: HTTP 500 от ссылки PDF сохранять
  как терминальный статус `server500`. Такой `doc_id` и день не запрашивать
  повторно, но обязательно оставлять дату, `doc_id`, причину и URL в логе и
  отчёте. Если у той же даты были другие ошибки, дату всё равно не повторять,
  а дополнительные статусы явно сохранить в чекпоинте и отчёте. Ошибки страниц
  выдачи на датах без HTTP 500 остаются повторяемыми.
- Окончательно считать документ не имеющим PDF только после HTTP 404/410.
  HTTP 200 с HTML, пустым или иным не-PDF ответом повторять и оставлять ошибкой,
  не позволяющей завершить день.
- Сначала сохранять PDF во временную папку `.nrat_work/<год>`, затем создавать
  временный ZIP, проверять число PDF и наличие манифеста, атомарно переименовывать
  архив и лишь после этого удалять временную папку года.
- Для объединения нескольких исходных/repair-ZIP использовать
  `consolidate_nrat_archives.py`: сверять множества и SHA-256 списка `doc_id`,
  выполнять CRC-проверку и сохранять отличающиеся байтовые варианты вместо их
  удаления.
- После сбоя повторный запуск должен продолжать работу по чекпоинту и не
  скачивать заново корректные PDF.
- В полном `--repair`-проходе неполный год нужно явно отметить в отчёте, но не
  останавливать последующие годы. После диапазона сохранять сводку всех
  незавершённых дат и ошибок для следующего повторного запуска.

## Табличные данные

- Для каждого года 1991–2025 должен существовать отдельный результат с одной и
  той же схемой колонок; объединение годов допустимо только как дополнительный
  результат.
- Полные таблицы строить `build_nrat_tables.py` непосредственно из канонических
  `../nrat pdfs/<год>.zip`. Старые неправильные `data/output_2017.csv` …
  `data/output_2025.csv` удалены из Git; не восстанавливать и не использовать
  их как результаты.
- Основной ключ строки — `doc_id`, а не регистрационный номер. Несколько PDF
  одного `doc_id` проверять как варианты, выбирать наиболее полный читаемый и
  сохранять полный список имён в `source_variants`.
- Ошибка чтения или пустые критические поля не должны удалять `doc_id` из
  результата: оставлять строку со статусом `warning`/`failed` и точной причиной.
- Крупные результаты хранить вне Git в `../outputs/nrat_excel_1991_2025`.
- После полного прохода запускать `validate_nrat_tables.py`: наборы `doc_id` и
  количество строк должны точно совпасть с годовыми ZIP.
- Сохранять украинский текст в UTF-8 с BOM для совместимости с Excel.
- При изменении извлечения не перезаписывать проверенные годовые результаты без
  явного пересоздания и сопоставления количества строк/колонок.

## Проверенное финальное состояние

- Актуальный снимок сайта и локальных данных проверен 23 августа 2026 года.
- Сайт показывает 183 352 публикации: 182 397 представлены PDF текущей
  годовой выдачи, 356 имеют подтверждённый статус `no_pdf`, 593 возвращают
  HTTP 500, ещё 6 позиций входят в счётчик, но не имеют доступного `doc_id` в
  выдаче. Контрольное равенство:
  `182397 + 356 + 593 + 6 = 183352`.
- В канонических ZIP находятся 183 608 физических PDF-вхождений и 182 622
  уникальных `doc_id`. Разница состоит из 986 дополнительных PDF-вариантов.
- Проверены все 986 группы вариантов: 985 пар совпадают по нормализованному
  тексту и отрисовке всех страниц; в одной паре 2016 года одна копия
  повреждена, но выбрана исправная. Разных публикаций, ошибочно объединённых
  под одним `doc_id`, и нерешённых случаев нет.
- В итоговых CSV ровно 182 622 строки и 182 622 уникальных `doc_id`; наборы
  `doc_id` CSV и ZIP совпадают. Есть 222 строки `warning` и одна строка
  `failed`: уникальный повреждённый PDF 2023 года
  `8c2291621873bda3bf520316f743a621`, у которого нет другой копии.
- Единый пользовательский пакет находится вне репозитория в
  `../FINAL_NRAT_1991_2025`. Его `03_REPORTS` разделён на категории
  `NO_PDF`, `HTTP_500`, `LISTING_GAPS`, `DUPLICATES`, `DAMAGED_PDF`,
  `EXTRACTION_WARNINGS`, `ARCHIVE_EXTRAS`, техническую проверку и сырые
  repair-логи.
- PDF-ZIP и итоговые CSV внутри финального пакета являются жёсткими ссылками на
  проверенные исходники. Не заменять их обычными копиями без необходимости:
  это повторно займёт около 46 ГБ.

## Что разрешено отправлять в Git

- Исходный код `*.py`, ноутбук
  `NRAT-Scraping&log-FULL-YEAR-clean.ipynb`, тесты `tests/`, `requirements.txt`,
  `.gitignore`, `README.md`, `AGENTS.md` и актуальный агрегированный
  `AUDIT_1991_2025.md`.
- Маленькие ручные примеры в `samples/` и уже отслеживаемые исторические логи
  в `data/` можно оставлять в репозитории. Удалённые
  `data/output_2017.csv` … `data/output_2025.csv` обратно не добавлять и не
  заменять ими финальные таблицы.
- Перед коммитом обязательно выполнять `git status --short`, `git diff --check`
  и тесты. В коммит должны входить только понятные изменения кода,
  документации и тестов.
- Динамический `_token` НРАТ получать только с сайта во время запуска. Никогда
  не коммитить фактические значения токенов, cookies, заголовки авторизации или
  другие данные сессии. В ноутбуке перед коммитом не должно быть output-ячеек.

## Что запрещено отправлять в Git

- `../nrat pdfs/`, любые `*.pdf`, годовые/repair `*.zip`, staging, резервные
  `_pre_consolidation_*` и временные рабочие каталоги.
- `../outputs/`, `../FINAL_NRAT_1991_2025/` и 35 полных
  `output_<год>.csv`: это итоговый набор данных объёмом около 46 ГБ вместе с
  PDF и он не предназначен для обычного GitHub-репозитория.
- `_repair_progress_*`, `_repair_errors_*`, `_repair_report_*`, общие
  repair-сводки, подробные списки ошибок, логи извлечения новых полных данных и
  локальные временные файлы.
- `.venv/`, `__pycache__/`, `.pytest_cache/`, `*.pyc`, `.ipynb_checkpoints/` и
  любые файлы с локальными секретами.
- Не использовать обычный Git для файлов около или больше 100 МБ. Если полный
  набор когда-либо понадобится публиковать, использовать отдельное хранилище,
  GitHub Release/Git LFS или репозиторий данных, а в Git оставить только ссылку
  и агрегированный отчёт.

## Проверка изменений

- Для загрузчика запускать `python -m py_compile download_nrat_pdfs.py` и
  локальные тесты функций без массовых запросов к сайту.
- Проверять, что ноутбук является валидным JSON и что все обычные Python-ячейки
  синтаксически корректны.
- Живой сетевой smoke-тест должен быть точечным; полный год не запускать в ходе
  разработки.
- Для финальной сверки запускать `audit_duplicate_publications.py`,
  `validate_nrat_tables.py`, `final_audit_1991_2025.py` и
  `make_final_package.py`. Все контрольные равенства должны быть `true`.
